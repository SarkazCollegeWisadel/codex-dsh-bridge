# Codex–DSH 双向协作桥：工程研究报告

日期：2026-11-03。研究对象：本仓库公开版本 0.3.0（源码基线 `cf268ea`）。这是可复现工程案例报告，不是同行评审论文，也没有建立模型能力提升的因果结论。源码及本文按仓库 MIT 许可证提供。

## 摘要

本项目研究如何让两个具有不同工作上下文的 Agent，在不复制私人会话历史的前提下交换任务与验收证据。实现采用固定会话绑定、本地 SQLite、显式任务修订、关联回信及可选事件唤醒。Codex 承担计划与代码审阅；DSH 在原会话整理上下文、执行获准操作和积累经审阅的经验。协议记录“谁收到什么版本”，业务完成仍由可核查结果决定。

既有验证记录报告 60 项合成测试通过，以及真实 DSH SDK 在独立临时 profile 中的六工具注册和调用验证。报告编写本轮未重跑这些检查；数字引用[验证记录](VALIDATION.md)，不代表新增生产验收。尚未验证公开版在全新机器上的完整安装、实际业务往返或跨平台自动唤醒。

## 1. 问题与研究问题

多 Agent 协作容易混淆四类状态：消息已入队、对端已接收、代码已修改、业务已验收。旧任务排队、同名会话、超时后重发以及缺少版本的“完成”回信，会进一步放大这种混淆。

本案例聚焦三个问题：

1. 如何明确识别当前任务和目标会话，并保留被替代任务的证据？
2. 如何恢复中断协作，同时限制重复派发及无信息量的互相确认？
3. 如何使下一位 Agent 根据有限笔记恢复审阅，而不读取私人历史？

不研究模型训练、临床有效性、自动答题效果或无人监督的生产决策。

## 2. 设计与实现

### 明确身份与任务版本

绑定使用双方固定会话 ID，不依赖聊天标题。workstream 区分同一会话里的独立工作。新任务显式记录 taskKey、taskRevision 和 supersedes；执行前重新检查 current/actionable。替代旧任务不会抹掉历史，也不保证已被宿主接受的动作能被撤销。

### 持久交付与不确定性

SQLite 保存消息、回复关联、回执及派发租约。同 ID 同内容幂等，同 ID 不同内容拒绝。超时保留 unknown，先核真实回执。跨宿主边界仍不能保证业务严格执行一次，业务操作必须另外设计幂等与恢复。

### 原会话投递与事件接续

DSH 插件通过持有会话的宿主排队投递，避免创建另一个执行宿主接管会话。可选 Windows 适配通过文件事件与桌面队列请求唤醒，空闲不使用周期模型保活。它不提供实时延迟保证；应用退出、睡眠、接口变化或额度耗尽仍会阻断推理。

### 审阅与学习的分工

Codex 核对计划、精确代码与测试证据；DSH 提供其环境中的授权执行结果。双方均可能犯错，不能把角色名称当作可靠性证明。推荐的记忆条目包含来源、适用版本、审阅状态、验证条件、纠正和撤回记录；这是知识管理建议，不是内置记忆系统或模型权重训练。

## 4. 复现与实际验收

在独立测试环境使用 Node.js 24+，从上述源码基线开始：

```sh
node --test test/*.test.mjs
npm pack --dry-run --ignore-scripts
git diff --check
```

SDK 探针依赖匹配的 DSH SDK；配置和 ASAR 环境要求见[验证记录](VALIDATION.md)。不要使用生产 profile 代替临时环境。

真实验收另按[安装指南](INSTALL.md)进行：核对运行版本及固定双方 ID，完成 Codex → DSH → Codex → DSH 四段关联，逐条检查消息 ID、回执与回复。启用事件适配时，必须看到目标聊天实际接收并回应新资料；worker 正在运行或 wake-requested 不能代替该证据。故障注入只使用合成任务。

## 5. 工程发现与限制

显式版本能使旧任务可识别，但无法消除宿主已接受的副作用；所以接收方的版本复核仍是必要步骤。持久化能保存断点，但“存得住”不等于“执行正确”。双重审阅增加发现错误的机会，当前没有对照实验量化其增益、成本或 token 节省。

桥以可信本地进程为边界，不是多租户安全服务或 OS 沙箱。文本模式筛查不是完整脱敏，classification 只是调用方声明。资料 SHA 能证明字节一致，不能证明内容安全或结论正确。

桌面适配仍为实验能力。当前没有延迟分布、长期失效率、吞吐基准或跨版本兼容矩阵，不能从合成通过率推导生产可靠性百分比。完整边界见 [LIMITATIONS.md](LIMITATIONS.md) 和 [SECURITY.md](../SECURITY.md)。

## 6. 可迁移工作流程

恢复笔记与当前版本 → 收取授权技术资料 → 核对计划和源码 → 执行最小必要验证 → 回传精确版本及证据 → 对端实际验收 → 核心复核闭环。

每项结果分别记录代码、测试、安装、运行版本与业务验收。两轮没有新增证据时保存具体阻碍，停止重复互问；新证据到达后从断点继续。生产变更使用精确文件清单、Git 与独立验证的回滚备份，不能用旧整库覆盖新会话任务。
